* [[file:../intro.org::As interfaces gráficas costumam ter estado][intro: As interfaces gráficas costumam ter estado]], p. N (cada evento roda uma parte do programa)
- Frase: “Num programa orientado a eventos, cada evento, seja a tecla
  digitada, o toque na tela, a requisição web, a chegada de um pacote da
  rede ou o tique do relógio, faz rodar uma parte do programa em resposta
  (Krishnamurthi; Fisler, 2019, p. N).”
- Trecho: “In contrast, in an event-driven program, it is the operating
  environment that is in charge; each event (whether a keystroke, a screen
  touch, a Web request, a network packet arrival, or the tick of a clock)
  causes some part of the program to run in response.” (seção 3, “Beyond Paradigms”)
- Lido em: =tmp/fontes/krishnamurthi2019.pdf=, p. 8 do PDF, a versão dos
  autores (“Draft of a chapter”); a página do livro (p. 377-413) espera a
  versão publicada.
- Observação: “it is the operating environment that is in charge” fica
  fora da frase: o “ambiente de execução” do =CONTEXT.md= é só o que faz as
  atualizações que o código declara, e não o /operating environment/ da
  fonte. Substitui Madsen, Lhoták e Tip (2017, 86:1), que fica em
  =prog.org= (decisão do autor em 2026-10-14).
- Conferido: 2026-10-14.
* [[file:../intro.org::As interfaces gráficas costumam ter estado][intro: As interfaces gráficas costumam ter estado]], p. N (o estado entre os eventos)
- Frase: “O desafio do programador é organizar como o estado passa de um
  evento a outro (Krishnamurthi; Fisler, 2019, p. N).”
- Trecho: “The programmer’s challenge is to arrange how state is
  transferred between the events.” (seção 3, “Beyond Paradigms”)
- Lido em: =tmp/fontes/krishnamurthi2019.pdf=, p. 8 do PDF, a versão dos
  autores.
- Observação: a frase seguinte da fonte diz que isso se faz de vários
  modos, “imperatively, using objects, functionally, reactively”, o que
  liga o estado aos modelos de programação comparados adiante.
- Conferido: 2026-10-14.
