#+TITLE: Implementações das interfaces

Cada interface do /benchmark/ de notação tem uma pasta, e cada tecnologia
uma subpasta: =implementacoes/<interface>/<tecnologia>/=. Cada subpasta é
um projeto completo, com o próprio =package.json=, e pode ser lida sozinha.
O escopo (interfaces e tecnologias) está nas decisões em
[[file:../docs/adr/][docs/adr/]]. O código que saiu da análise (o Contador,
a Lista filtrável, o Carrinho, o jQuery, o Angular com RxJS, o JavaFX com
FXML, o par Qt Widgets × QML e o cronômetro de 2017) fica congelado em
[[file:fora-da-analise/README.org][fora-da-analise/]], fora dos comandos
abaixo.

* Pré-requisitos: Node.js e JDK

  As versões ficam em =.tool-versions=, na raiz do repositório, e o
  [[https://asdf-vm.com][asdf]] as instala:

  #+begin_src sh
  asdf plugin add nodejs
  asdf plugin add java
  asdf install
  #+end_src

  O Angular 22 exige Node 22.22.3 ou mais novo. O JDK (Temurin 25) só é
  preciso para o Android e o desktop.

* Instalar e rodar (web)

  Os projetos web são /workspaces/ do npm, todos em TypeScript: um único
  =npm install= em =implementacoes/=, onde está o =package.json= dos
  /workspaces/, instala todos. Os comandos =npm= abaixo rodam de
  =implementacoes/=. O =build= confere os tipos com =tsc= antes de
  empacotar.

  #+begin_src sh
  npm install
  npm run dev -w formulario/react
  #+end_src

  Troque o caminho pelo da implementação desejada. O Vite serve em
  =http://localhost:5173= e o Angular em =http://localhost:4200=.

  | Subpasta           | Tecnologia                             |
  |--------------------+----------------------------------------|
  | =web-component=    | DOM puro com /custom element/ (classe) |
  | =react=            | React                                  |
  | =solid=            | Solid (/signals/)                      |
  | =lit=              | Lit (sobre o /custom element/)         |
  | =angular-signals=  | Angular com /signals/                  |

* Instalar e rodar (Android)

  O Formulário com validação também existe no Android, em Kotlin, em duas
  tecnologias:

  | Subpasta           | Tecnologia                                         |
  |--------------------+----------------------------------------------------|
  | =android-views=    | Views clássico: /listeners/, estado na =Activity= |
  | =android-compose=  | Jetpack Compose                                    |

  Todos formam um único projeto Gradle, com raiz em
  =implementacoes/android/=, onde ficam o /wrapper/ e as versões
  (=gradle/libs.versions.toml=). Cada subpasta é um módulo, chamado
  =:<interface>-<tecnologia>= (por exemplo, =:formulario-android-compose=).

  Precisa do Android SDK (o Android Studio o instala em =~/Android/Sdk=),
  com a plataforma =android-37= e as /build-tools/ 36.0.0. Para compilar
  pela linha de comando, crie =implementacoes/android/local.properties= (não é
  versionado; o Android Studio o cria ao abrir o projeto):

  #+begin_src sh
  echo "sdk.dir=$HOME/Android/Sdk" > implementacoes/android/local.properties
  cd implementacoes/android
  ./gradlew assembleDebug                                   # todos os APKs
  ./gradlew :formulario-android-compose:installDebug         # instala no emulador
  #+end_src

  No Android Studio, abra a pasta =implementacoes/android/=.

  | Peça              | Versão     | Por quê                                           |
  |-------------------+------------+---------------------------------------------------|
  | JDK               | Temurin 25 | LTS; o Gradle roda no 25 desde a 9.1               |
  | Gradle            | 9.7.0      | máximo com suporte completo do Kotlin 2.4.20       |
  | AGP               | 9.3.3      | linha 9.3, a última com suporte do Kotlin 2.4.20 |
  | Kotlin            | 2.4.20     |                                                   |
  | Compose BOM       | 2026.09.00 |                                                   |
  | Robolectric       | 4.17       | suporta a API 37 (notas da versão)                 |
  | Roborazzi         | 1.75.0     |                                                   |

  A compatibilidade entre Kotlin, Gradle e AGP segue a tabela de
  [[https://kotlinlang.org/docs/gradle-configure-project.html][kotlinlang.org/docs/gradle-configure-project.html]]; havia Gradle 9.8 e AGP
  9.4 mais novos, fora dela.

* Instalar e rodar (desktop)

  O Formulário com validação também existe no desktop, em Java, em duas
  tecnologias, com a tela montada em código nas duas:

  | Subpasta  | Tecnologia                                       |
  |-----------+--------------------------------------------------|
  | =swing=   | Swing: /listeners/, estado na classe da tela     |
  | =javafx=  | JavaFX 27: /properties/ e /bindings/, sem FXML   |

  Os dois formam um único projeto Gradle, com raiz em
  =implementacoes/desktop/=, onde ficam o /wrapper/ e as versões
  (=gradle/libs.versions.toml=). Cada subpasta é um módulo, chamado
  =:<interface>-<tecnologia>= (por exemplo, =:formulario-swing=). O
  domínio é o =dominio-kotlin= do Android, compilado para a JVM e chamado
  do Java.

  #+begin_src sh
  cd implementacoes/desktop
  ./gradlew test                            # testes de conformidade e cenas
  ./gradlew :formulario-javafx:run          # abre a janela
  #+end_src

  Os testes rodam sem janela: o Swing pinta a tela numa imagem, e o
  JavaFX usa a plataforma Headless.

* Capturas de tela

  Cada interface guarda capturas versionadas em
  =implementacoes/<interface>/capturas/=, uma por tecnologia e cena
  (=react-inicial.png=, =android-compose-erros.png=...). Ao criar ou alterar
  uma implementação, gere-as de novo e inclua no mesmo commit: o =git diff=
  mostra o que mudou na tela.

  #+begin_src sh
  npx playwright install chromium-headless-shell   # só na primeira vez
  npm run capturas                                  # todos
  npm run capturas -- formulario                    # uma interface
  npm run capturas -- formulario/react              # uma implementação
  npm run capturas -- formulario/android-views      # uma implementação Android
  npm run capturas -- --conferir                    # só compara, não grava
  #+end_src

  O =--conferir= gera as imagens numa pasta temporária, compara com as
  versionadas e lista as que mudaram, as novas e as que sumiram, saindo com
  erro se houver alguma. Rode antes de commitar uma alteração numa
  implementação: se algo mudou de propósito, regenere; se não, é regressão.

  As cenas de cada interface ficam em
  =implementacoes/<interface>/cenas.mts= (ações do Playwright antes da
  captura); sem ele, só o estado inicial é capturado. O /script/
  ([[file:capturar.mts][implementacoes/capturar.mts]]) faz o /build/, serve
  o resultado, fixa a data em 26/09/2026 (para "hoje" não mudar a imagem)
  e, no fim, avisa se a mesma cena saiu diferente entre as tecnologias web
  de uma interface, o que indica que alguma implementação foge da
  especificação.

  No Android, as mesmas cenas ficam nos testes de cada módulo
  (=src/test/.../CenasTest.kt=). O /script/ roda esses testes pelo Gradle
  com [[https://robolectric.org][Robolectric]] e
  [[https://github.com/takahirom/roborazzi][Roborazzi]], que desenham a
  tela na JVM, sem emulador, e o resto segue igual: mesma pasta, mesmo
  =--conferir=. O aviso compara só Views com Compose. As duas reproduzem o
  =estilo.css= da interface, cada uma no seu arquivo de estilo
  (=res/values/estilo.xml= no Views, =Estilo.kt= no Compose), mas desenham
  o texto com diferenças de poucos pixels, e o aviso aparece mesmo assim:
  abra as imagens e confira se posições, cores e conteúdo batem. As
  animações ficam desligadas nos testes: o efeito de toque (/ripple/) tem
  um brilho que mudaria a imagem a cada execução.

  No desktop, as cenas ficam em =src/test/.../CenasTest.java= de cada
  módulo, e o /script/ as roda pelo Gradle de =implementacoes/desktop/=,
  sem janela. As imagens saem no tamanho da janela, 416 × 560, sem a
  escala 2 da web e do Android, que o Swing não mede sem janela. O aviso
  compara Swing com JavaFX e sai sempre: cada um desenha controles e
  texto a seu modo, cada um com o seu arquivo de estilo (=Estilo.java= no
  Swing, =javafx-estilo/estilo.css= no JavaFX).

  Agentes de código seguem essas regras pelo
  [[file:AGENTS.md][implementacoes/AGENTS.md]] (o =CLAUDE.md= ao lado é um
  /symlink/ para ele).

  As imagens web dependem das fontes instaladas: geradas noutra máquina,
  podem mudar sem que o código tenha mudado, e as do desktop também. As do
  Android usam as fontes que o Robolectric traz.

* Especificação das interfaces (OpenSpec)

  A especificação de cada interface fica em
  =implementacoes/openspec/specs/<interface>/spec.md=, no esquema
  /spec-driven/ do [[https://openspec.dev][OpenSpec]] (1.14.1, fixado em
  =package.json=): requisitos e cenários, em português, com os cabeçalhos
  que o OpenSpec lê em inglês. A mudança entre rodadas é uma pasta em
  =implementacoes/openspec/changes/=, com a proposta e o /delta spec/;
  arquivada, ela se funde na especificação viva e vai para
  =changes/archive/=. A mudança dentro de uma rodada edita o =spec.md=
  direto. A convenção está no
  [[file:AGENTS.md][implementacoes/AGENTS.md]].

  #+begin_src sh
  npm run conferir-especificacao          # validate e cenários × testes
  npm run openspec -- new change <nome>   # cria a pasta de uma mudança
  npm run openspec -- show <nome>         # mostra uma spec ou mudança
  npm run openspec -- archive <nome> --yes
  #+end_src

  O =npm run openspec= desliga a telemetria do OpenSpec
  (~OPENSPEC_TELEMETRY=0~), que vem ligada; o comando =openspec= direto a
  envia.
